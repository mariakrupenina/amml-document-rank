# AMML Document Ranking – история экспериментов

В работе решалась задача ранжирования текстовых документов по релевантности поисковому запросу в **AMML Ranking Competition 2026**. Качество оценивалось по **NDCG@10**: для каждого запроса рассчитывается качество порядка первых десяти документов, затем результат усредняется по запросам.

Ниже собраны промежуточные эксперименты, полученные метрики и причины выбора итогового подхода. Описание относится к реально проведённым проверкам; неподтверждённые улучшения не рассматриваются как результат финальной модели.

## 1. Данные и подготовка

Исходный обучающий набор состоял из **31 530 документов по 3 042 запросам**, тестовый – из **13 507 документов по 1 305 запросам**. В обучающей части находились 8 168 документов с меткой `relevance = 1` и 23 362 с меткой `0`.

Поскольку один запрос связан с несколькими документами, разделение выполнялось по `query_id`, а не по отдельным строкам. Так документы одного запроса не попадали одновременно в обучение и отложенную оценку.

| Выборка | Запросов | Документов |
|---|---:|---:|
| Fit | 2 408 | 24 944 |
| Validation | 329 | 3 426 |
| Dev | 305 | 3 160 |

Для ранжирования заголовок (`title`) объединялся с текстом статьи (`text`), результат ограничивался **1 800 символами**. Пропущенные значения заголовка заменялись пустой строкой.

При анализе тестовых данных обнаружились фрагменты с повреждённой кириллицей (ошибочная интерпретация кодировки). Исправление выполнялось только тогда, когда после преобразования уменьшалось число признаков повреждения. Таким образом были исправлены **72 документа из 70 тестовых запросов**. Обучающие тексты этим преобразованием не изменялись.

## 2. Исходная Jina и выбор обучающих примеров

В качестве основы использовалась предобученная **`jinaai/jina-reranker-v3.5`**. Сначала модель рассчитала оценки релевантности для **21 052 документов из 2 033 запросов**. Они использовались не как целевые метки, а для отбора сложных отрицательных примеров.

Один из обнаруженных эффектов – зависимость оценок от порядка документов внутри запроса. Поэтому сравнивались два прохода:

- **Forward** – документы в исходном порядке;
- **Reverse** – документы в обратном порядке с последующим восстановлением соответствия оценок документам.

Оценки каждого прохода стандартизировались по Z-score внутри запроса и усреднялись. Этот приём далее использовался и при оценке дообученной модели.

### Hard Negative Mining

Случайный нерелевантный документ обычно не представляет для модели большой сложности. Поэтому для обучения формировались группы максимум из четырёх документов: до двух релевантных, один *hard negative* (нерелевантный документ с высокой оценкой базовой Jina) и дополнительные случайные примеры. Когда исходных оценок Jina для запроса не было, отрицательные документы выбирались случайно. Порядок документов в группе перемешивался.

Первоначальная процедура дополняла короткие группы повторными документами. В результате появились **40 искусственно дублированных позиций** для 21 запроса. Перед обучением эти повторы удалили, чтобы они не влияли на функцию потерь как дополнительные наблюдения.

В окончательной обучающей выборке получилось **9 592 документа в 2 408 группах**:

| Размер группы | Количество групп |
|---|---:|
| 4 документа | 2 387 |
| 3 документа | 2 |
| 2 документа | 19 |

## 3. Дообучение Jina с LoRA

Полное дообучение всех параметров модели было избыточно по вычислительным затратам, поэтому использовалась **Low-Rank Adaptation (LoRA)**. Обновлялись только адаптеры проекций внимания `q_proj` и `v_proj` – **1 146 880 параметров**, около **0,192%** всех параметров модели.

| Параметр | Значение |
|---|---|
| Базовая модель | `jinaai/jina-reranker-v3.5` |
| LoRA rank / alpha / dropout | `8 / 16 / 0` |
| Обучаемые модули | `q_proj`, `v_proj` |
| Оптимизатор | AdamW |
| Learning rate | `2e-5` |
| Weight decay | `0.01` |
| Эпохи / шаги | 1 / 2 408 |
| Функция потерь | Listwise cross-entropy, `score_scale = 8.0` |
| Gradient clipping | `1.0` |
| Точность | FP16 |
| Ограничение документа при обучении | 192 токена |

Списковая функция потерь учитывала документы одного запроса совместно, а не обучала модель независимо на каждой паре. Это соответствовало задаче: важна не отдельная оценка, а взаимный порядок документов.

В новом запуске средний loss последних 50 шагов составил **0.8322** против **1.0559** на первом шаге. Значения loss использовались для контроля обучения, а окончательное сравнение проводилось по NDCG@10 на отложенных запросах.

### Базовая модель против LoRA

В архиве предыдущей версии сохранились оценки базовой Jina и дообученной LoRA на одинаковых **329 Validation-запросах**. Дополнительно проверялось усреднение их оценок.

| Вес базовой Jina | Вес LoRA | Validation NDCG@10 |
|---:|---:|---:|
| 100% | 0% | 0.956228 |
| 75% | 25% | 0.961085 |
| 50% | 50% | 0.964950 |
| 0% | 100% | **0.969685** |

Дообучение улучшило качество с **0.956228 до 0.969685** (разница **+0.013457**). Подмешивание базовой модели обратно ухудшало результат. По этой причине базовые оценки оставили для отбора hard negatives, а основным ранжировщиком стала LoRA.

## 4. Выбор способа ранжирования

После повторного обучения сравнивались три способа инференса: Forward, Reverse и их среднее после стандартизации внутри каждого запроса.

| Способ | Validation NDCG@10 | Dev NDCG@10 |
|---|---:|---:|
| Forward | 0.964010 | 0.964440 |
| Reverse | **0.970361** | 0.966902 |
| **Forward + Reverse (Z-score, 50/50)** | 0.969755 | **0.968230** |

Только Reverse дал максимальный результат на Validation, но на Dev оказался слабее комбинации двух проходов. Двунаправленное ранжирование выбрали как более сбалансированный вариант по двум отложенным выборкам.

Важно, что **192 токена** – ограничение, использованное при подготовке документов *для обучения*. При Validation, Dev и Test модель получала тексты до **1 800 символов**, без повторной ручной обрезки до 192 токенов.

Первая отправленная версия Jina с LoRA дала **0.966072** на Public Leaderboard. Позднее был выполнен повторный запуск обучения и получена обновлённая версия, показавшая **0.966579**. Прирост на Public составил **+0.000507**. Локальные оценки этой модели – **0.969755** на Validation и **0.968230** на Dev; эти значения рассчитаны на других запросах и не должны смешиваться с Public Score.

## 5. Как менялся подход в ходе работы

Решение не строилось сразу вокруг Jina и LoRA. Сначала я проверила более простые способы оценки релевантности, затем перешла к специализированным моделям ранжирования и только после этого занялась дообучением. На каждом этапе сравнивала качество с предыдущим вариантом по NDCG@10. Ниже описаны основные изменения и причины, по которым я продолжала эксперименты.

### 5.1. Первый вариант и переход к E5

Начальная версия давала **0.773157** на Public Leaderboard. Это была отправная точка: стало понятно, что базового подхода недостаточно, чтобы уверенно различать документы, близкие по теме, но не одинаково полезные для ответа на запрос.

Следующим шагом я попробовала **E5**, модель текстовых представлений. Качество выросло до **0.844654** (**+0.071497**). Этот результат показал, что семантическое сопоставление вопроса и документа работает лучше первоначального варианта, но запас для улучшения ещё оставался.

Затем проверила совместное использование **E5 и BGE**. Оно подняло Public NDCG@10 до **0.927032** (ещё **+0.082378**). На этом этапе я убедилась, что сочетание оценок разных моделей может существенно менять качество порядка документов. Однако эти модели ещё не давали того уровня точности, который хотелось получить на верхних позициях выдачи.

### 5.2. Переход к Jina и проверка дополнительных признаков

После экспериментов с текстовыми представлениями я перешла к **Jina Reranker v3.5**. В отличие от сопоставления независимых эмбеддингов, reranker оценивает запрос и документ совместно, что больше соответствует задаче выбора наиболее релевантной статьи из набора кандидатов.

Один из промежуточных вариантов сочетал оценки **Jina и LightGBM**. Он показал **0.949995** на Public Leaderboard (**+0.022963** относительно предыдущего лучшего результата). Это был заметный прирост, но дальнейшее усложнение за счёт дополнительных моделей не выглядело обязательным: сначала стоило разобраться с особенностями самой Jina.

### 5.3. Влияние порядка документов

При работе с Jina обнаружилось, что оценка может зависеть от того, в каком порядке документы передаются модели. Поэтому я попробовала делать два прохода: в исходном порядке и в обратном, а затем сопоставлять оценки одним и тем же документам.

Такой двунаправленный инференс дал **0.950679** на Public (**+0.000684**). Прибавка была небольшой, но подход позволял использовать дополнительную информацию без переобучения и впоследствии оказался полезен для LoRA. Позже я отдельно проверила прямой, обратный и объединённый проходы на Validation и Dev; результаты этого сравнения приведены в разделе 4.

### 5.4. Исправление проблем с текстом

Следующим этапом стала проверка входных данных. В части тестовых документов встретилась повреждённая кириллица: некоторые русские фрагменты были неправильно декодированы. Для модели это означало потерю нормального текстового контекста даже там, где подходящая статья присутствовала среди кандидатов.

Я добавила избирательное исправление кодировки и сравнила результат с предыдущей версией. После обработки качество выросло с **0.950679 до 0.952550** (**+0.001871**). Это показало, что ошибки в данных могут заметно влиять на качество ранжирования, даже если сама архитектура модели не меняется.

### 5.5. Подготовка сложных примеров и дообучение LoRA

После исправления входных текстов основной резерв качества я стала искать уже в адаптации модели к конкурсной разметке. Вместо полного обучения всех параметров выбрала **LoRA**, а для формирования обучающих групп использовала **Hard Negative Mining**. Идея состояла в том, чтобы показывать модели не только очевидно нерелевантные документы, но и те, которые сама базовая Jina ошибочно оценивала высоко.

Перед обучением я также проверила состав групп и удалила искусственно повторённые документы, чтобы дубликаты не влияли на списковую функцию потерь. Детали отбора примеров и параметры обучения приведены в разделах 2 и 3.

Дообученная Jina с исправленной кодировкой и двунаправленным инференсом получила **0.966072** на Public Leaderboard. По сравнению с предшествующим вариантом без LoRA это **+0.013522**. Этот прирост оказался одним из наиболее значимых на позднем этапе работы и подтвердил, что обучение на сложных отрицательных примерах полезнее простого объединения дополнительных сигналов.

### 5.6. Повторное обучение и проверка воспроизводимости

После первого успешного обучения я повторила эксперимент с той же основной схемой: Jina v3.5, LoRA и объединение оценок прямого и обратного проходов. Для новой версии получила **0.969755 на Validation** и **0.968230 на Dev**. На Public Leaderboard она показала **0.966579**, что на **0.000507** выше предыдущего лучшего результата.

Разница между двумя запусками небольшая. Поэтому я не рассматриваю её как доказательство того, что повторное обучение само по себе гарантированно улучшает модель. Но результат подтвердил, что выбранный подход воспроизводится и остаётся конкурентоспособным при новом запуске.

Таким образом, за время работы Public NDCG@10 вырос с **0.773157 до 0.966579**, то есть на **0.193422**. Это результат последовательности разных экспериментов, а не одного изменения. Самый существенный вклад на поздних этапах внесло дообучение Jina с LoRA, поэтому именно этот вариант стал основой итогового решения. Проверка альтернативных ансамблей после обучения описана отдельно в разделе 6.

## 6. Проверка альтернатив финальной LoRA

После получения новой модели отдельно проверялись другие варианты ранжирования. Для сопоставимости все значения ниже рассчитаны на тех же наборах запросов. Вес ансамбля подбирался на Validation, после чего выбранная комбинация проверялась на Dev. Это важно: хороший результат на Validation сам по себе не доказывает улучшение на новых данных.

### 6.1. Ансамбль старой и новой финальных LoRA

Старый адаптер был восстановлен из сохранённого checkpoint 2408. Его оценка на Dev **0.967461** совпала с историческим результатом, то есть восстановление весов и метода инференса было корректным.

| Вариант | Validation | Dev |
|---|---:|---:|
| Старая LoRA | 0.969685 | 0.967461 |
| Новая LoRA | 0.969755 | **0.968230** |
| Старая 50% + новая 50% | **0.970012** | 0.967643 |

Несмотря на прирост на Validation, ансамбль ухудшил Dev на **0.000587**. Из 305 Dev-запросов улучшились 5, ухудшились 15, остальные 285 не изменились. Парный bootstrap на Validation дал 95% интервал изменения **[−0.000647; +0.001202]**, содержащий ноль. Устойчивого преимущества не обнаружено.

### 6.2. Промежуточные checkpoint 400, 800 и 1600

Проверялись сохранённые состояния старого обучения. По мере увеличения числа шагов качество отдельных адаптеров росло:

| Checkpoint | Forward, Validation | Reverse, Validation | Combined, Validation |
|---|---:|---:|---:|
| 400 | – | 0.963472 | – |
| 800 | 0.961089 | 0.966105 | 0.965796 |
| 1600 | 0.965177 | **0.968856** | 0.968635 |
| 2408 | – | – | 0.969685 |

Прочерк означает, что соответствующий вариант отдельно не рассчитывался. Затем наиболее интересные оценки Reverse смешивались с новой LoRA.

| Ансамбль | Validation | Dev |
|---|---:|---:|
| Новая 90% + checkpoint 400 Reverse 10% | 0.970893 | Не проверялся |
| Новая 75% + checkpoint 800 Reverse 25% | **0.971713** | 0.967510 |
| Новая 75% + checkpoint 1600 Reverse 25% | 0.971212 | **0.968520** |

Лучший Validation дал checkpoint 800, но на Dev сочетание снизило NDCG относительно новой LoRA на **0.000720**. Checkpoint 1600, напротив, дал небольшой прирост на Dev **+0.000290**. Однако улучшились только 7 запросов, ухудшились 12, а 286 не изменились.

Для ансамбля с checkpoint 1600 95% bootstrap-интервал прироста на Dev составил **[−0.000895; +0.002096]**. Ноль находится внутри интервала, поэтому статистически убедительное преимущество перед новой LoRA не подтверждено.

### 6.3. Анализ ошибок

На Validation у новой LoRA **83 из 329 запросов** имели NDCG@10 меньше 1, а в **15 запросах** документ на первом месте уступал по разметке другому документу. Детально разбирались случаи, где модель выбирала тематически близкий текст вместо ответа:

- **«Где находится золотой запас США?»** – выше оказалась статья о запасах золотой руды, а не о хранилищах золотого резерва.
- **«Есть ли море в городе Находка?»** – модель предпочла статью об одноимённой бухте в Карском море статье о городе.
- **«Какое животное является самым древним на Земле?»** – документ о находке возрастом 350 млн лет обогнал текст о находке возрастом 428 млн лет.
- **«В каком году вышел Манифест „Об усовершенствовании государственного порядка“?»** – документ с подходящим заголовком не содержал даты в основном фрагменте текста, а релевантный по разметке документ её указывал.

Ни один из пяти подробно рассмотренных проблемных запросов не содержал сравниваемых документов длиннее 1 800 символов. Следовательно, эти ошибки нельзя объяснить обрезкой хвоста текста. Основная наблюдаемая трудность – различение **наличия ответа** и **общей тематической близости**.

### 6.4. Дополнительный лексический сигнал (TF-IDF)

Проверялась добавка символьного TF-IDF по n-граммам длиной 3–5 символов. Оценка нормализовалась внутри запроса и смешивалась с новой LoRA.

| Вес TF-IDF | Validation NDCG@10 | Изменение |
|---:|---:|---:|
| 0% | **0.969755** | 0 |
| 5% | 0.969083 | −0.000672 |
| 10% | 0.967945 | −0.001810 |
| 20% | 0.961294 | −0.008461 |

Все ненулевые веса ухудшили качество. Совпадение формулировок не гарантировало наличие точного ответа, поэтому TF-IDF не включали в итоговое ранжирование.

### 6.5. Независимая BGE Reranker

Дополнительно проверялась многоязычная модель **`BAAI/bge-reranker-v2-m3`**. Она исправила 3 из 5 специально выбранных ошибок Jina, однако на полной Validation работала значительно слабее.

| Вариант | Validation | Dev |
|---|---:|---:|
| Новая Jina LoRA | 0.969755 | **0.968230** |
| BGE отдельно | 0.929466 | 0.928690 |
| Jina 90% + BGE 10% | **0.972582** | 0.967677 |

Несмотря на высокий результат Validation, ансамбль ухудшил Dev на **0.000553**: 12 запросов улучшились, 20 ухудшились. Добавление BGE не подтвердило своего преимущества на второй выборке.
